# LiteLLM Routing Lab

A cost-aware AI gateway that routes each request to the cheapest Gemini model that can
actually handle it — with measured latency and spend evidence rather than intuition.

Deployed on Google Cloud Run, backed by Cloud SQL PostgreSQL, and configured entirely
as code.

## The problem

A company ships an AI feature and sends every request to the strongest model. Simple
prompts ("reply with the word blue") and genuinely hard ones ("reason about when to
choose queues over synchronous APIs") cost exactly the same. As traffic grows, so does
the waste.

This project measures that waste, then removes it.

## Architecture

```
                            ┌──────────────────────────┐
  benchmark.py ──POST──────▶│  Cloud Run: litellm-      │
  (4 fixed prompts)         │  gateway  (public, TLS)   │
                            └────────────┬─────────────┘
                                         │ virtual key auth + budget
                                         ▼
                            ┌──────────────────────────┐
                            │  LiteLLM proxy 1.104.0   │
                            │  model_list in config    │
                            └───┬──────────────────┬───┘
              model: jev-router │                  │ model: gemini-flash
                                ▼                  ▼
                    ┌───────────────────┐   ┌──────────────┐
                    │ complexity_router │   │   Vertex AI  │
                    │ classifier: jev   │   │  Gemini 3.5  │
                    └─────────┬─────────┘   └──────────────┘
                              │ SIMPLE / MEDIUM / COMPLEX / REASONING
                              ▼
                    ┌───────────────────────────────┐
                    │ Flash-Lite  ← SIMPLE, MEDIUM  │
                    │ Flash       ← COMPLEX, REASON │
                    └───────────────────────────────┘
```

Persistence layer: Cloud SQL PostgreSQL 15 stores virtual keys, router config, request
logs, and spend records, mounted into the container at `/cloudsql`.

## What makes it interesting

**The routing decision is inspectable.** `return_raw_model_name: true` means a routed
response reports the concrete Gemini deployment that actually served it, not the alias
`jev-router`. Routing stops being a black box.

**Classifier failure degrades safely.** `circuit_breaker_enabled: true` with a 30-second
cooldown, plus `classifier_fallback: default_model`, means a Jev outage sends traffic to
the default strong model rather than breaking requests. It fails toward correctness.

**Secrets never enter the image.** The master key, salt key, and database URL are
generated by Terraform, written to Secret Manager, and injected at runtime. Credentials
exist in no file and no image layer.

**Spend is capped, not just observed.** A `$1` virtual-key budget acts as a hard
guardrail; exceeding it is expected to return HTTP 422. (Not yet confirmed against a live
deployment — see the runbook's Secret Mission step.)

## Checking it offline

No Terraform, gcloud, or Docker is required to run these:

```bash
python tools/check_structure.py   # 178 structural checks
python tools/test_checker.py      # 11 negative tests: proves the checker bites
```

`check_structure.py` verifies balanced HCL delimiters, unterminated strings, project-wide
resource reference resolution, YAML indentation, that all four router tiers point at
declared aliases, and that `benchmark.py` still exposes `run_case`/`main`.

**It is not `terraform validate`** — provider schema errors can still slip through. It
catches the failure class that matters for hand-assembled config: the typo that costs you
twenty minutes in Cloud Shell.

## Deploy

Full step-by-step instructions are in [`RUNBOOK.md`](RUNBOOK.md). Short version,
run from Google Cloud Shell:

```bash
cp terraform.tfvars.example terraform.tfvars   # then set your project_id
terraform init && terraform validate
terraform apply -target=google_artifact_registry_repository.images
docker build -t "$IMAGE_URI" . && docker push "$IMAGE_URI"
terraform apply                                 # ~15 min, Cloud SQL dominates
```

Then open `terraform output -raw admin_url`.

## Benchmark

The same four prompts run twice — once pinned to `gemini-flash`, once through
`jev-router` — so the comparison isolates routing as the only variable.

```bash
export LITELLM_BASE_URL="$(terraform output -raw service_url)"
export LITELLM_API_KEY="$(gcloud secrets versions access latest --secret=litellm-api-key)"
python3 benchmark.py baseline   # writes benchmark-baseline.csv
python3 benchmark.py routed     # writes benchmark-routed.csv
```

Each row records `case`, `expected_tier`, `requested_model`, `returned_model`,
`latency_ms`, and `classifier_cost_header`.

## Cost

Infrastructure targets **under $5** if destroyed within two hours. Cloud SQL compute and
storage are the only meaningful standing charges. Note that the `$1` LiteLLM virtual-key
budget caps gateway traffic only — it does **not** cap Google Cloud billing.

To tear down:

```bash
terraform destroy
gcloud secrets delete typesafe-api-key   # created outside Terraform
```

## Notes and caveats

- **Verify the model IDs before deploying.** `config.yaml` ships with
  `vertex_ai/gemini-3.5-flash` and `vertex_ai/gemini-3.5-flash-lite`, copied from the
  source project. I could not confirm those identifiers exist in Vertex AI, and there is
  public evidence against it — see the StackOverflow report that BigQuery rejects a
  `gemini-3.5-flash` model and the `gemini-cli` issue on `gemini-3.5-flash` failing over
  Vertex. The catalogue appears to offer `gemini-3-flash` and `gemini-2.5-flash` /
  `gemini-2.5-flash-lite`. Step 3 of the runbook checks this against your own project and
  tells you how to substitute. The aliases (`gemini-flash`, `gemini-flash-lite`,
  `jev-router`) are what the router references and do not change — only the `model:`
  lines under `litellm_params`.
- **Nothing was validated locally beyond syntax.** This repository was authored on Windows
  with no `terraform`, `gcloud`, or `docker` available. `main.tf` has **not** passed
  `terraform validate`, and no `terraform plan` or `apply` has been run. Treat the first
  `terraform validate` in Cloud Shell as the real check.
- `terraform.tfvars`, `*.tfstate`, and `benchmark-*.csv` are gitignored. No credentials
  are committed.
